# 12 个检查维度（完整定义）

每个维度绑定三样东西才可执行：**判定方法**（怎么查）、**证据形式**（拿什么证明）、**通过标准**（什么算过）。评审 agent 在阶段 1/2 按此逐维度检查；协调者按"机械 → 语义 → 治理"的顺序安排。

## 维度 1：结构完整性（脚本）

- **判定方法**：`inventory_docx.sh` / `inventory_xlsx.py` + raw XML 检查。docx：章节编号连续、无跳号重号、标题层级一致、表格行列完整、目录域存在、无空段异常聚集。xlsx：合并区域连续无空洞、数据验证/条件格式/公式范围覆盖全部数据行、无隐藏行（除非设计如此）、定义名称无 `#REF!`、行序连续（重点查"行号存在空洞但前后都有数据"——这是插行回归的典型形态）。
- **证据形式**：inventory JSON + raw XML 片段（如 `<x:row r="177"...>` 存在而 `r="178"` 缺失）。
- **通过标准**：结构断言全真；发现任何"数据行之间的无格式空行"即为 P1。
- **真实案例**：某检查单两条数据行之间缺失一行，类别合并区横跨空行，表格被无格式空行切断——插入行时跳过了原有的空分隔行。

## 维度 2：声明与实物一致（脚本 + agent）

- **判定方法**：用 `claim_scan.py` 生成声明登记表初稿，逐条补裁定。覆盖：条目/段落/表格计数、严重级别分布、列数、版本号、日期、文档 ID、"新增/删除了 X"的陈述。摘要类文档（修改摘要、评审报告）里的数字同样登记——它们与实物不符是最常见的 P0。
- **证据形式**：claims.csv 中每行有 verify_method、observed、verdict；计数类附实测命令。
- **通过标准**：每条声明有裁定；任何"真"裁定都要能复现。
- **真实案例**：摘要称"编号改为文本"（实测数值）、"补齐 5 条"（实际 3 条）、"H 71 / M 83"（实测已变）、"剩余 123 条提示"（实测 128）。

## 维度 3：引用存在性（脚本）

- **判定方法**：内部引用全量对照（如检查单 Ref. 列 ↔ 指南实际章节号集合）；外部链接逐个请求（`check_links.py`）。链接判定要区分：200（有效）、404（失效，注意跟随重定向后的最终状态）、403/406（可能反爬虫拦截，标注"需浏览器人工复核"，不算失效）。
- **证据形式**：引用对照表；链接报告含状态码与最终 URL。
- **通过标准**：0 悬空引用；0 确认失效链接。
- **真实案例**：某文档引用的官方链接重定向后仍 404；同一清单中另一站点返回 403 但页面实际正常（反爬拦截），两者处置完全不同。

## 维度 4：引用支撑性（agent，只读）

- **判定方法**：对每条引用，取被引目标的**原文**与引用方的陈述比对：被引条款是否真的支撑该要求。警惕"相邻原则顶替"——引用一个主题相关但内容不覆盖的条款。
- **证据形式**：引用方陈述 + 被引原文摘录 + 支撑/不支撑结论。
- **通过标准**：抽到全量（L3）或分层抽样（L2，抽样须随机且覆盖各类别，不许挑顺眼的）；不支撑的列为弱映射。
- **真实案例**："安全评审记录可追溯"引用了只说明两文件配套关系的章节；"完整性校验（SHA-256/HMAC）"引用了漏洞分类章节而非算法表。

## 维度 5：外部文档核验（agent + 人）

- **判定方法**：引用公司内部文档时，解析该文档**自身的元数据**（封面 Document ID、版本、标题、目录结构），核对引用编号与描述；文件名只作定位线索。"是否仍现行/已废弃"标记为需文档管理员确认，不假装核验。
- **证据形式**：原件封面单元格值 + 引用处文本；关键词计数（描述声称的内容在原件中的出现次数）。
- **通过标准**：编号与描述均与原件一致；现行性有人签字确认。
- **真实案例**：引用编号用了文件名写法（多一个下划线）；描述某流程"含漏洞分级、修复时限与对外披露"，原件关键词 `severity/disclos/SLA/timeline` 计数全为 0，实际是补丁管理流程。

## 维度 6：事实与时效（agent）

- **判定方法**：事实账簿：标准版本（OWASP/ASVS/NIST/RFC/ISO）、工具产品状态（停产/更名/归档）、CVE/RFC 编号、日期。来源等级：官方源 > 厂商文档 > 二手资料；**模型记忆不得单独作为依据**。带版本号的事实每轮重查。
- **证据形式**：每条事实附来源 URL 与核查日期。
- **通过标准**：全部事实有官方源支撑；过期的标记并给出现行版本。
- **真实案例**：`NIST SP 800-63B-4（2025-07 终版）`、`OWASP Top 10 2025（2025-11-06）`、`ASVS 5.0.0（2025-05-30）` 均经官方站核实为真；`JSHint 停止维护`（末版 2022-11）经多方确认。

## 维度 7：内部一致性（脚本 + agent）

- **判定方法**：同一标识在封面/修订历史/审批表/页眉页脚/交叉引用/姊妹文件中的写法与取值逐一比对；同名概念同写法；两份配套文档（如指南与检查单）之间的口径比对。
- **证据形式**：一致性矩阵（标识 × 出现位置 → 值）。
- **通过标准**：全站同值同写；不一致项要么修正、要么记录为已知差异并说明权威值。
- **真实案例**：文档 ID 在封面（带 &）、页脚、检查单引用、文件名四处写法不一——不一致是继承的，统一它属于治理决策（走维度 10）。

## 维度 8：覆盖完整性（脚本 + agent）

- **判定方法**：建双向矩阵：指南章节 ↔ 检查单条目 ↔ 活动矩阵 ↔ 外部标准条款。找三类缺口：①文档正文无对应检查项的章节；②活动矩阵中无检查项的活动；③标准要求在两份文档中都无落地。反向：检查项引用的支撑是否存在（并入维度 4）。
- **证据形式**：覆盖矩阵 + 缺口清单（每项注明"单向缺失"还是"双向皆无"）。
- **通过标准**：缺口为空，或有记录在案的理由（含"按适用性判定"的说明）。
- **真实案例**：等级矩阵 14 项活动中"加固基线核查""ASVS 自查"两项在 172 条检查项中命中数为 0；映射规则遗漏一个类别，导致该类别条目无法按等级裁剪。

## 维度 9：语义质量（agent + 参照系）

- **判定方法**：每条要求过四个问题：①可验证（存在可观测证据，不是口号）②适用（覆盖适用对象、不越界、不与文件定位冲突）③有依据（标准条款/内部制度/风险评估，**判断必须引用参照**）④成本匹配（与项目等级/风险相称）。
- **证据形式**：判断 + 参照引用；无参照的判断不成立。
- **通过标准**：抽样的每条要求四问全过或给出修改建议；无"我觉得"式结论。
- **真实案例**："严重 7 天"的修复时限严于 PCI DSS v4（30 天）——不是错误，但必须标注为取舍点并交由人确认。

## 维度 10：治理与合规（人）

- **判定方法**：列出所有治理敏感项：文档标识/编号规范、基线与审批、复审周期、语言策略、法规适用（PIPL/GDPR/行业监管）、客户合同约束。**agent 只生成决策问题（选项 + 默认建议 + 代价），不代替人决定。**
- **证据形式**：决策记录（问题/选项/决定/理由/影响文件）。
- **通过标准**：所有治理项已由人回答并签字。
- **真实案例**：单方面统一文档 ID、决定"编号规范化"——方向可能对，但决策权不在评审 agent；正确产物是决策问题 + 记录。

## 维度 11：交付完整性（脚本）

- **判定方法**：`integrity_gate.sh`：officecli validate + issues 计数、占位符扫描（TODO/TBD/lorem/`{var}`/`$xxx$`/xxx）、`###` 溢出标记、工具残留属性（`OfficeCLI.*`）、打印/页面设置存在性。
- **证据形式**：门禁输出（每项 PASS/FAIL）。
- **通过标准**：validate 通过；0 占位符；残留为 0（final_clean 之后复测）。
- **真实案例**：officecli 每次保存都重写 `OfficeCLI.Version/LastModified`（只读访问触发的驻留刷新也会）——不清理就交付，会带工具元数据进正式文档。

## 维度 12：回归与差异（脚本 + agent）

- **判定方法**：`diff_snapshot.py diff` 比对修复前后快照；逐块差异对照接受清单，分三类：应改已改（对应某 finding）/ 应改未改（遗漏）/ 不应改而改（回归）。文本级 diff 之外的变更（哈希变了但文本没变的：格式、属性、元数据）单独列出。
- **证据形式**：差异报告 + 分类标注。
- **通过标准**：0 未解释差异；0 回归。发现回归 → 回阶段 4，计入轮次上限。
- **真实案例**：修复后 COUNTA 公式范围没有覆盖新增行（应改未改）；条件格式子串误命中在修复中被引入又被发现（回归）。
