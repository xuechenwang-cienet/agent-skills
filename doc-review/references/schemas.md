# 数据结构定义

三个核心结构 + 一个返回格式。字段齐全才算完成；缺字段的不进入下一阶段。

## 1. 声明登记表（claims.csv）

评审的主战场不是通读，而是核验声明。把文档及其摘要里所有可核验的陈述登记成行，逐条裁定。

CSV 列定义（首行表头固定）：

```csv
claim_id,source_file,location,type,claim_text,verify_method,observed,verdict,evidence,checked_by
```

| 字段 | 说明 |
|---|---|
| claim_id | `C-001` 递增 |
| source_file | 声明所在文件 |
| location | 行号 / 章节号 / 单元格 / 段落 ID |
| type | `number`（计数）/ `id`（文档标识）/ `version` / `date` / `link` / `quote`（引述）/ `existence`（存在性陈述，如"新增了 X 章节"） |
| claim_text | 声明原文（截取关键片段） |
| verify_method | 核验命令或动作（可复现） |
| observed | 实测值 |
| verdict | `true` / `false` / `unverifiable`（附原因：内网地址、需管理员确认等） |
| evidence | 命令输出片段或来源 URL |
| checked_by | 脚本名或 agent 名 |

规则：`claim_scan.py` 只生成初稿（前 5 列）；裁定列由评审 agent 填写；`unverifiable` 必须写明卡在哪一步、需要谁。`false` 裁定自动生成一条 P1 以上发现。

## 2. 发现（finding）

单条发现的结构（01-findings.md 中每条一节）：

```markdown
### F-001 <一句话标题>
- 维度: <12 维之一>
- 严重度: P0|P1|P2|P3
- 文件: <路径>
- 位置: <可唯一定位：章节号/单元格/行号/段落 ID>
- 观察值: <实测是什么>
- 期望值: <应该是什么，依据是什么>
- 证据: <命令 + 输出片段；或来源 URL + 日期>
- 复现: <可直接粘贴执行的命令>
- 建议动作: <具体到目标文本/单元格的修改建议>
- 状态: proposed
```

硬规则：八项字段缺一即退回；"疑似""大概"不许出现——要么给证据，要么改写为"待确认 + 需要执行的检查"。

## 3. 编辑规格（edit spec，04-fix-summary.md 的核心节）

修复执行的唯一依据。executor 只做规格里的事；规格与实际不符时停下报告，不自行发挥。

```markdown
### E-001（对应 F-003，accepted）
- 文件: <路径>
- 定位: <officecli 路径 / 单元格地址 / find 锚文本（注意：自动列表的"•"不在文本里，锚文本不要带它）>
- 修改前: <精确原文>
- 修改后: <精确目标文本>
- 验证: <命令> → <预期输出>
```

另附结构性操作（插行/移动/范围调整）：操作类型、目标位置、联动项清单（合并区域、校验范围、公式范围——插行必须列全）。

## 4. sub-agent 返回格式（上下文经济契约）

每个 sub-agent 完成后**只**返回：

```
产出: <文件路径列表>
摘要: ≤10 行（P0/P1 计数、关键结论、需要人决策的问题数）
异常: <无 | 停下的步骤与原因>
```

全文、明细、命令输出一律留在工件文件里。协调者不读 sub-agent 的过程对话。

## 5. manifest.json（快照清单，脚本生成）

```json
{
  "created": "ISO8601 时间",
  "files": [
    {"path": "相对路径", "sha256": "…", "size": 12345, "mtime": "…"}
  ]
}
```

用途：终审 diff 的比对基线；"原件未被改动"的证明（对照原始 manifest 的哈希）。
